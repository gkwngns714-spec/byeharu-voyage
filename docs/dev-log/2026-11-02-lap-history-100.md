# 2026-11-02 — The lap history is 100 (migration 0301)

**The owner's order (2026-11-02, verbatim):** *"route lap history - we actually don't need this. 100 would be good"*

`public.world_config` key `standing_route_lap_keep` is **200** (since 0097; 30 before). Migration
`20260818000301_the_lap_history_is_100.sql` sets it to **100**. That is the one knob change the owner authorised: no other knob, switch,
cron job or schedule moves, no function is touched, no row is purged and no table is rewritten by this file.

## 1. What ships

One `UPDATE` of one `world_config` row (`value = to_jsonb(100)`, the description with its history, `updated_at = now()` — the table has no
`updated_at` trigger; the only trigger on it fires for `time_compression`), and a self-assert in the same `DO` block (the runner is not a
transaction block, so a statement outside the block would survive a failed assert). Guard: `statement_timeout` 90 s, `lock_timeout` 5 s; the knob
must read exactly 200, or already 100 (re-runnable); any other value is the owner's and the file refuses.

The trim is **lazy and already written**. The knob has exactly one reader, `cmd.standing_route_close_lap(uuid, timestamptz)`. At every lap close
it deletes, for that route only, `lap_no <= <the lap just closed> - public.wc_int('standing_route_lap_keep')`. Once the knob reads 100 each route
therefore trims itself to its newest 100 closed laps at its **next** lap close. Nothing else is needed, and the file does not run it.

## 4. What a viewer sees differently — said plainly

* **A human player: nothing.** The only player-owned route has never closed a lap, and every sheet a player's own route reads needs ten laps or fewer
  — until that route is short enough to close more than 100 laps in a day.
* **A merchant route that closes 100 or more laps in a day is cut short.** Its newest 100 laps cover less than 24 hours (at 160 laps a day, 15 hours;
  at 328, 7 hours), so on the Routes board and the merchant sheet its "a day" becomes "so far" over fewer hours — the sheet already prints
  *So far · over the last <span>* when `day_full` is false, so the shorter figure is labelled, not hidden — and the figure is smaller than the
  real 24-hour net. **34 routes today, about 278 (37 %) at the quiet-disk rate.** Every one is a merchant's.
* **The Stats tab's merchants block counts the laps still on file.** `profit_day`, `laps_day`, `losing_pct`, top/bottom and each house's day and
  laps would count up to **18 % fewer laps** at the quiet-disk rate (the laps beyond each fast route's newest 100), and a house with fast routes
  reads smaller. They are not wrong sums of what is on file; they are sums over less than 24 hours for those routes.
* **Nothing else moves:** lap numbers, the all-time book (`route_month_laps`, so `laps_done` and `total`), the newest 7 / 10 laps and their trades
  (`standing_route_lap_trades_keep` stays 7), money, orders, events.

What would keep "a day" whole on the fastest routes is a keep at least as large as their laps a day (328 at the quiet-disk rate; 132 in the last
24 h), or reading the day from a rollup instead of lap rows. **That is the owner's call and is not done here**: the order was 100.

## 5. The trim, and what happens to the table afterwards

* **When.** Each route trims at its own next lap close. At the quiet-disk rate a route closes a lap every 10–20 minutes, in the busy hours every
  30 minutes on average, so most routes are done in the first hour; a laid-up or paused route trims when it next closes a lap; the 2 routes that hold
  fewer than 100 do not trim at all.
* **How much.** About 100 rows a route × 837 = **~84,000 deleted** in that hour; the table goes from 167,587 to **~84,500 rows** (837 × 101) and then
  stays near it, because every close deletes what falls past 100.
* **Load.** ~84,000 deletes in an hour is about the volume the table already inserts and updates in an hour (1,500–2,800 closes, each an insert and an
  update); each lap delete probes `orders_route_lap` (nothing to null) and `standing_routes_open_lap_fk` (the open lap is never trimmed). The deletes
  leave dead tuples in the table the Stats count reads; `standing_route_laps` has `autovacuum_vacuum_threshold = 500` (0291), so autovacuum runs
  often while it trims (expect more passes than the usual ~2 an hour) and keeps the visibility map fresh for the index-only 24-hour read. Watch the
  Stats count's `merchants` phase (1.3–1.6 s now) during that hour — see the after-check.
* **The heap keeps its size.** 227 MB stays 227 MB: the freed room is reused by new laps, nothing returns to the operating system. **A later
  migration compacts the table** (a rewrite with a fillfactor, as 0292 did for `port_goods`); this file does not, on purpose.

## 6. The self-assert (and its budget)

In one `DO` block, after the one update: **(a)** the knob reads exactly `100` (jsonb number; `wc_int` and `wc_num` agree) and
`standing_route_lap_trades_keep` still reads 7; **(b)** every *other* `world_config` row is unmoved — one md5 over key, value, description and
`updated_at` of every row but this one, before = after, and the row count; **(c)** the closer is still the only function that names the knob and its
live text still holds the per-route delete against the knob, once; all 678 functions in public/cmd/world/voyage are md5-unmoved (count and one md5
by identity); **(d)** the registry (84 entry points), the walls (0 / 0 / 0), `economy_closed` and `city_treasury_enabled` as found; **(e)** this
transaction made no scan, fetch, insert, update or delete on `standing_route_laps` (its own `pg_stat_xact` counters, before = after). It reads the
catalog twice and the 291-row knob table twice: milliseconds, independent of the size of any real table. It never runs a real step and never reads a
lap row.

## 8. After-check (read-only; for the coordinator, ready to paste)

```sql
-- 1. the knob (expect 100, updated_at = the deploy)
select value::text as keep, updated_at from public.world_config where key = 'standing_route_lap_keep';
select value::text as trades_keep from public.world_config where key = 'standing_route_lap_trades_keep';          -- 7, unmoved

-- 2. laps per route: expect max 201 -> <= ~101 and avg 200 -> ~100 within ~45-60 minutes (a laid-up route trims when it next closes a lap)
select max(c) as max_per_route, round(avg(c)) as avg_per_route, count(*) as routes,
       count(*) filter (where c > 101) as routes_still_over_101
  from (select count(*) c from public.standing_route_laps group by route_id) x;

-- 3. the table: n_live_tup should fall from ~167k to ~84k; dead tuples rise then fall; run it twice, 10 minutes apart, and subtract
--    autovacuum_count (expect a few more passes than usual while it trims)
select n_live_tup, n_dead_tup, autovacuum_count, last_autovacuum, n_tup_del, now() as at
  from pg_stat_user_tables where relid = 'public.standing_route_laps'::regclass;
select reltuples::bigint as reltuples, relpages, pg_size_pretty(pg_relation_size(oid)) as heap
  from pg_class where oid = 'public.standing_route_laps'::regclass;                                              -- the heap stays ~227 MB

-- 4. the Stats count during the trim (merchants phase 1.3-1.6 s before; > 10 s is a stop-and-look)
select at, ms, receipt->'phases'->>'merchants' as merchants_ms from public.stats_runs order by at desc limit 6;

-- 5. a one-off exact count (an after-check may; a migration may not)
select count(*) from public.standing_route_laps;                                                                  -- ~84,500 once every route has closed a lap
```
