## What is deliberately NOT here, and the server read it needs

**Per-leg sea requirements.** Which seas each leg crosses, and what they ask, live in `public.sea_leg_asks` (0215,
`from_port, to_port, wave_min, title_min`) and `public.harbour_zone` / `public.course_zones`. **No client read exposes
them.** `world.sea_conditions()` serves the zones and their asks but not which zone a harbour or a course is in. The
client could find out only by re-running `sea_zone_at` over the boxes and then comparing `title_min > title`,
`wave_min > wave`: that is a second copy of `public.sea_refusal`, which the task forbids.

Decided by default: print the player's own figures (title, ships, wave) and the switch state, and no per-leg
verdict. **The read that would add it** (a migration, not this lane): `world.good_board`'s buy and sell rows gain
`sea: { zone, zone_name, needs_title, needs_wave, refusal }` for the passage they serve, read from `sea_leg_asks` along
the served `stops` and judged by `public.sea_refusal` **even while dark** (so the requirement can be shown as
informational, marked "not in force yet", and is the server's own answer when lit). The face then prints the server's
figures per leg and never compares them.

**A known wording gap once lit (not built here).** When `sea_conditions_bite` is lit, 0216's `voyage.reach_passage`
shuts edges by `sea_leg_asks`, so a row closed by the SEA arrives as `sailable: false, stops: null`, and `reachWords`
would then say "too far to sail in one go". That is the board's existing wording meeting a new cause. The same
`sea` field above would let `reachWords` say the true reason. It must land before the switch is lit.
