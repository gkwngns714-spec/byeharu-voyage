# OWNER REQUESTS — the open ledger

> **Closed rows (LIVE / done / closed / withdrawn / rejected / reversed) are in `docs/OWNER_REQUESTS_DONE.md`, word for word, under the same table header.**

**Why this file exists.** On 2026-08-23 the owner said: *"last time you messed up not doing
everything i told you. Do not make the same mistake again."* They were right, and the cause is
structural, not attentional: a list of instructions held in a conversation is **lost at the next
context compaction**, and this project has already lost instructions that way twice — once producing
*"what i said before to make, nothing is done"*, once *"then all the sayings that i did, you didn't
make them? what else you didn't do?"*.

So the list lives here, in the repo, where it survives compaction and can be diffed.

**The rules for this file**

1. **Every instruction from the owner gets a row, in their own words**, the moment it is given.
   Paraphrasing is how an instruction quietly narrows. Quote them.
2. A row leaves `OPEN` only when the thing is **built AND verified in the running game** — not when
   an agent reports it done. An agent report is a claim, not proof.
3. A row that is **refused or deferred** does not get deleted. It gets a state and a reason, so the
   owner can overrule it. Silently dropping something is the failure this file exists to prevent.
4. `DONE` rows stay for one release, then move to the bottom under `SHIPPED`. The file is not a
   changelog — `docs/DEV_LOG.md` is — but a request must be visibly closed rather than vanish.
5. **An instruction that has to be given again is a bug report about this file.** It means the row
   was wrong, or it was closed without being verified. Diagnose the row and say what went wrong.
   **Do not tally how many times it was said** — the count is not the finding, and this file is a
   record of the work, not a score kept against the owner.

**And the mirror of rule 5, found 2026-09-06.** Three rows — **51**, **53** and **63** — were still reading `OPEN` / `in progress` while the work sat merged on `main`, two of them since 2026-09-01. Nobody gave the instruction again; the file simply went quiet about work that was done, which is the same failure pointing the other way: a row that lies about being unfinished spends the next session re-planning something already built. **The pattern is specific and it is checkable: all three landed in CLIENT-ONLY pull requests** (#9/#11, #13, #16), and a client-only PR touches no migration — so it slips past the one habit that reliably makes someone open this file. `docs/DEV_LOG.md` has no entry for those three either, for exactly the same reason. **So: a slice with no migration owes this file and the dev log the same two edits a slice with one does.**
