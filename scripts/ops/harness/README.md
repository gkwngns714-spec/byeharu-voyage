# Ops harness, kept for re-use

These are the scratch tools behind the 2026-10-18/19 measurements, copied from `~/dev/bv-harness` so they travel with the repo. They are **not** part of the build or CI. Source only: the 3 GB of worlds and node_modules they generate stay local and are rebuilt by `setup.mjs`.

- `more-ships/` is 0366 (Wave E, 54 hulls): `gen-0366.mjs` writes the migration, `before.sql`, `after.sql` (both read-only on prod) and `rollback-0366.sql` (a draft) from the generator's Wave E, and `--check` holds the four to it until the deploy; `proof-0366.mjs` (red first, the real file and proof 67 green, the old-rows and functions digests of `before.sql` unmoved by the file, 15 mutations red, cached world); `duels.mjs` fights the new hulls through `public.fight_sides` on the cached world (each against two older hulls both ways round; `--matrix` the jobs against each other and fleets against raids); `tables.mjs` prints the dev-log's tables; `q.mjs` runs SQL files on the cached world in a rolled-back transaction (`--before=<migration>` stops the chain short).
- `raid/after-check.sh <start> <end>` is the PAIRED fight after-check, run READ-ONLY on prod. It compares each lit raid against the dark table on the same raid, prints the arrivals, reconcile and queue figures, and ends with a PASS or FAIL line. Run it after any change that lights or rebalances combat.
- `raid/paired.sql` is the query behind it. `raid/sim.mjs` replays prod's raids through `voyage.fight_resolve`.
- `sim/` holds the prod-shaped merchant world (`setup.mjs`, `prodlike.mjs`, `sim.mjs`, `measure*.mjs`). It keys loops by company and fleet. The older `laps-scratch` copy keyed them by fleet name, which was a bug.
- `haul/` is the `haul_max` sweep of 2026-10-20 (0212): `sweep.mjs` lays the arrfast world over an image, applies the
  migrations, then measures `bands.sql` (the far-selling metric: a competent trader's best profit per day by route band)
  for each candidate value in a rolled-back transaction; `sum.mjs` prints the medians and the long ÷ short ratios.
- `speed/` is the 0220 pair of 2026-10-25 (ship speed ×3): `prep.mjs` lays the arrfast state over a merchant world, applies
  the migrations prod applied after that state and dumps the common ground ONCE; `arrfast/sim.mjs` with `ARRFAST_SETUP=0`
  then runs each arm on that dump (the after arm applies the migration under test before the kickoff); `players.mjs` +
  `player.sql` measure a starter's day (days quoted, ducats per real hour and laps per real day by band, through the game's
  own speed authority) before and after the migration in one rolled-back transaction.

## Two classes: every SQL file here says which one it is (2026-11-08)

`tests/harness.guard.spec.ts` reads every `*.sql` under this folder (comments and literals stripped, so a hunk `$h$ … $h$` full of write words is data) and fails the tree when a file does not declare its class:

- **PROD CHECK**: a pure read, run against the live game with `npx --yes supabase@2.120.0 db query --linked -f <file>`. Its first statement is `begin transaction read only;` and its last `commit;` (the older `raid/`, `sim/` and `arrfast/` files close with `rollback;`, the same thing for a transaction that wrote nothing), so Postgres itself refuses any write the file turns out to hold; it calls only functions the chain declares `stable` or `immutable`.
- **LOCAL SCENE**: anything that writes (insert, update, delete, merge, truncate, create, alter, drop, grant, revoke, copy, refresh, call, perform, execute, explain analyze) or calls a function the chain does not declare stable or immutable: the `dark-scene.sql`, `cost.sql` and `parity-scene.sql` files the proof runners roll back, the kept copies of live bodies (`live_*.sql`, `settle_live.sql`, `prod_*.sql`, `old_legl.sql`, `new_*.sql`, `priceloop.sql`, `cand-*.sql`) and the migration drafts (`m0201.sql`, `0186.next.sql`, `tpl186.sql`). Its first statement is THE GUARD, exactly this line:

  `do $$ begin if inet_server_addr() is not null then raise exception 'local PGlite world only: this scene writes'; end if; end $$;`

  `inet_server_addr()` is null on PGlite (no server address) and never null on a Supabase connection, so a scene run on production refuses before its second statement. A migration never carries the guard: strip it before copying a draft into `supabase/migrations/`.

**The shell scripts ask the same reader (2026-11-12).** `read-only.mjs` holds the reader the spec imports and is the one judge of "this file is a read-only prod check": `node read-only.mjs <file.sql>` exits 0, or prints `REFUSING: …` with the reason and exits 3. Its rule: with comments gone and every literal one word, the FIRST statement is `begin transaction read only` (any case, CRLF or LF, a header comment of any length), the LAST is `commit` or `rollback`, and no statement holds a write verb or `explain analyze`. Every script that sends a file to production (`raid/after-check.sh`, `combat-log/after-check.sh`, the three `pq.sh`) asks it first; the spec fails a script that does not, or that counts bytes (`head -c`) as they did until `combat-log/after.sql`'s 700-byte header stopped the 0353 after-check. It does not judge volatility: that is `volatility.sql` on prod and the spec on the tree.

Two pure reads are neither, each tied to the runner that executes it with `db.query` inside its own rolled-back transaction (a wrapper in the file would commit the runner's work): `haul/bands.sql` (`haul/sweep.mjs`) and `speed/player.sql` (`speed/players.mjs`).
